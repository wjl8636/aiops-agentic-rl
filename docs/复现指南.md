显存优化组合：LoRA + gradient checkpointing + `bf16` + DeepSpeed ZeRO-2（`sft/` 的 YAML 里已经把这几项配好，`# deepspeed: ...` 那一行注释掉了，显存紧张时取消注释）。**不要用 FlashAttention-2**：Qwen3.5 的 Gated DeltaNet 线性注意力层依赖 `fla`（flash-linear-attention），这个库对 Triton/torch 版本极敏感，实测跑通的稳定组合是 `torch==2.14.0` + `triton==3.8.0` + `flash-linear-attention==0.5.2`，训练/部署配置里 attention 实现统一填 `sdpa`（标准注意力层走 PyTorch 自带 SDPA，线性注意力层走 fla 的 Triton kernel），不装 flash-attn 本体——牺牲一点训练速度换稳定性。版本冲突的具体报错和排查过程见 [`训练踩坑记录.md`](训练踩坑记录.md) 第三节，装环境时直接按这套组合装，不用重新踩一遍。

## 2. 装框架

三个框架都不在 `requirements.txt` 里（`requirements.txt` 顶部的注释解释了原因：版本对 CUDA/驱动强耦合，写死在仓库里反而会误导，只在租卡机器上装）：

```bash
# 0. 固定 torch/triton/fla 版本组合（见上一节，Qwen3.5 的线性注意力层强制 import fla，
#    版本不对会在 import 或 Triton kernel 编译阶段直接报错）：
pip install torch==2.14.0 triton==3.8.0 flash-linear-attention==0.5.2
pip uninstall -y deepspeed   # 单卡显存够用不需要它；装着的话 LLaMA-Factory 加载 Qwen3.5 时会被无条件 import 拖垮

# 1. Qwen3.5-9B text-only checkpoint 准备（先做这一步，其它两个框架都要用它）
python3 sft/load_text_only.py --model-dir <原始 Qwen3.5-9B 多模态 checkpoint 目录> \
    --output-dir /data/models/qwen3.5-9b-text-only
# 用 Qwen3_5ForCausalLM（不是 Qwen3_5ForConditionalGeneration）只加载语言主干,
# re-save 后得到无视觉权重的版本。
# 跑完之后，把原始多模态 checkpoint 目录下的两个小文件复制回 text-only 目录（不含视觉权重，
# 只是配置文件；LLaMA-Factory 给 Qwen3.5 系列模板硬编码了 processor 校验，没有这两个文件会报
# `Processor was not found`，跟数据集是否含图片无关）：
cp <原始多模态 checkpoint 目录>/preprocessor_config.json /data/models/qwen3.5-9b-text-only/
cp <原始多模态 checkpoint 目录>/video_preprocessor_config.json /data/models/qwen3.5-9b-text-only/

# 2. LLaMA-Factory（SFT）
git clone https://github.com/hiyouga/LLaMA-Factory.git
cd LLaMA-Factory && pip install -e ".[torch,metrics]"
# 把本仓库的数据集注册进 LLaMA-Factory：
# 先跑 data/cold_start/to_llamafactory_format.py 产出真实的 aiops_cold_start_sft.jsonl，
# 再把 data/cold_start/dataset_info_snippet.json 的内容合并进
# LLaMA-Factory/data/dataset_info.json（sft/train_sft.sh 里写了具体的合并步骤）。

# 3. veRL（GRPO）
git clone https://github.com/volcengine/verl.git
cd verl && pip install -e .
# grpo/verl_config/aiops_grpo.yaml 每个字段标了 [VERIFIED]/[ASSUMED]/[JUDGMENT]。单卡
# A800 拓扑下三个关键点已经真机核实过（第 6.1 节详细讲，直接照抄配置即可，不用重新核对）：
#   - rollout.name 用 vllm（不是 sglang），multi_turn 工具调用解析已经打了必要的 patch。
#   - custom_reward_function 的适配层在 grpo/verl_reward_adapter.py，已按真实调用惯例写好。
#   - actor_rollout_ref.model.lora_target 的模块名（对照 transformers v5.15.1 官方源码
#     modular_qwen3_5.py 核实）：Qwen3.5 每层是 full_attention（q/k/v/o_proj，标准命名）或
#     linear_attention（Gated DeltaNet，命名是 in_proj_qkv/in_proj_z/in_proj_b/in_proj_a/
#     out_proj）二选一，sft/llamafactory_config/qwen3_5_9b_lora_sft.yaml 和 GRPO 这边的
#     lora_target 都已按两种层的真实命名补全。
# 如果你用的是多卡经济档拓扑（而不是单卡 colocate），上面这些显存/并发参数需要重新过一遍
# 排查思路，不能直接照抄单卡数值。

# 4. vLLM（GRPO rollout + 最终服务化部署都要用）
pip install vllm
```

## 3. 种子池：v9 真实规模 47 新采 + v8_base 28 保留 = 63 条通过

`data/seeds/generated/` 下已经提交了 v9 阶段真实生成的种子告警，v9 训练侧真正用到的是"新采 47 条 seed × Opus 76 次 API 调用（通过率 74%，35/47 accepted）+ v8_base 保留 28 条 = 63 条通过轨迹"，经质量过滤 / BGE 语义去重 / 分层切分后落在 `data/clean/split/`（`train/` 74 条、`held_out/` 22 条），克隆仓库就能拿到，不需要你从头生成。

如果你想扩大规模或者加新的场景类型，用下面的命令重新生成（会覆盖 `data/seeds/generated/`，注意先备份；`--count` 换成你实际打算采集的规模，v9 阶段新采就是 47）：

```bash
python3 -m data.seeds.generate_seeds --count 47 --out-dir data/seeds/generated
python3 -m data.clean.filter --in-dir data/seeds/generated --out-dir data/clean/filtered
python3 -m data.clean.dedup --in-dir data/clean/filtered --out-dir data/clean/deduped
python3 -m data.clean.split --in-dir data/clean/deduped --out-dir data/clean/split
```

`data/seeds/generate_seeds.py` 顶部的模块 docstring 详细写了"哪个候选轴要加宽"——参数化扩增把 `_dependency_recipes()`/`_resource_cpu_recipes()`/`_queue_backlog_recipes()`/`_deploy_regression_recipes()` 里的 service 列表/阈值列表/时间窗列表加宽；flagd 组合扩增切到遍历 `itertools.combinations` 的全量组合；历史工单反演对 `HISTORICAL_INCIDENT_SUMMARIES` 做同义改写或真实检索 Milvus。三路的分配比例按当前池子分布自然形成，扩量时按需重新校准。

**一个真实踩过的坑,扩量时要留意**：单纯加宽阈值/lag/topic 这类数字型候选轴，产出的文本在 BGE 语义去重眼里几乎是"同一句话换个数字"，0.92 阈值下会被判定大量语义重复，参数化扩增这条路径的存活率明显低于历史工单反演（真正改写不同叙事，文本独立性更高）和 flagd 组合。如果你重新生成后发现语义去重存活率远低于预期，大概率不是代码或环境问题，而是"参数化扩增"路径本身的语义多样性天花板——想要更高存活率，给参数化扩增写更多"真正不同措辞"的模板变体（而不是更多数字组合），或者更依赖历史工单反演/flagd 组合这两条路径。

`dedup.py` 的 BGE 语义去重需要装 `sentence-transformers`（`requirements.txt` 已包含）；模型下不动时（国内环境常见，AIops-agent 那份教学文档也提过 HuggingFace 下不动的坑）会走 `dedup.py` 内置的 hash 近似降级路径。想用真 BGE，参考 AIops-agent 的经验改用 ModelScope 下载。

## 4. 真实 Cold Start 轨迹采集：仓库已经带了两批真实通过的轨迹

仓库提交的 `data/cold_start/aiops_cold_start_sft_v9.jsonl`（667 条 SFT 样本，604 tool_call + 63 diagnosis）是 63 条真实通过拒绝采样的轨迹展开来的——真实调用 Opus API + 真实 docker 环境采集，跨依赖/资源/队列/发版/config 等多类场景验证跑通，每条稳定收敛在 2~25 步。这批数据真实训出 checkpoint `aiops-qwen3.5-9b-v9-merged`（评测报告目录 `aiops-qwen3.5-9b-v9_20260908`：13 场景×37 行复评，service/kind/route = 0.5676/0.6757/0.4595，fix_success_rate 0.6667），随后 GRPO 接着这个合并模型继续训，产出本文档、`训练踩坑记录.md` 里报告的 GRPO checkpoint `aiops-qwen3.5-9b-grpo-step15`（详见第 6、7 节；完整的技术方案设计文档放在[飞书](https://zcnii5t1bwjj.feishu.cn/docx/G8H0dadMmoBmVJx445OcVVI1nxh)）。对应的人工标注 ground truth 在 `data/cold_start/ground_truth/`，`train`（74）/`held_out`（22）每条一份 GT。

如果你想扩大这批数据（比如覆盖更多场景、把某个 `remediation_type`/`kind` 补厚），才需要走下面真实采集这一段，前置条件缺一不可：

1. **真实 Claude API key**（`ANTHROPIC_API_KEY` 或已登录的 `claude` CLI），且账户有真实预算——v9 阶段 63 条通过轨迹一共实花 $58.77（预算 $60，是训练侧全部 API 支出），单条采集成本约 6-7 元人民币（$58.77 / 63 ≈ $0.93 / 条），建议先用个位数小批量跑通再放量。
2. **真实 AIops-agent 运行环境**：跟着 [AIops-agent 的 README](../AIops-agent/README.md) 起本地 kind 集群或 docker 后端，`AIops-agent/scripts/fetch-otel-demo.sh` 拉好 OTel Demo，`AIops-agent/scripts/seed-github.sh` 建好带泄漏 commit 的公开仓。
3. 确认 `claude_agent_sdk` 已安装（本仓库开发环境**故意没装**，因为装了就有真实调用风险；实际采集要在装好 SDK 的环境里跑）。

真实模式跨依赖/资源/队列/发版/config 等多类场景都已验证跑通，每条稳定收敛在 2~25 步、基本不超时。`real_mode()` 还会在跑每条告警前，根据告警的场景标注自动往活环境注入对应的真实故障（翻 flagd 开关 / 换故障 fixture 容器），跑完立刻复位，不需要你手动去复现每条告警描述的故障状态——这一层对诊断 Agent 不可见（喂给 Agent 的告警内容不含场景标注，不会泄漏答案）。

先跑环境检查（不发起任何真实调用）：

```bash
python3 -m data.cold_start.collect_trajectories --check-env
```

确认通过后，真实批量采集（`--alerts-dir` 换成你要补的那批新告警所在目录）：

```bash
python3 -m data.cold_start.collect_trajectories \
    --alerts-dir data/clean/split/train \
    --sample 47 \
    --out-dir data/cold_start/trajectories
```

这一步的核心工程细节（详见 `collect_trajectories.py` 模块 docstring）：因为 `AIops-agent/agent/core/sdk_runner.py::run_sdk()` 只在消息流里挑最终的 `ResultMessage`，中间每一步的工具调用和观测都被丢弃，所以本脚本绕开 `diagnose()` 封装，直接调 `claude_agent_sdk.query()`，把 `AssistantMessage.content` 里的 `ToolUseBlock` 和随后 `UserMessage.content` 里同 `tool_use_id` 的 `ToolResultBlock` 配对，还原出完整的 step 序列；同时用一层"偷看"包装 hook（先调一次真实的 `remediation.classify_command()` 记录判定结果，再原样转发给真正的 `guard_diagnose_ops`）拿到每一步真实的 allow/deny，**不改变任何放行/拦截行为**。

采集完跑拒绝采样：

```bash
python3 -m data.cold_start.rejection_sample \
    --traj-dir data/cold_start/trajectories \
    --ground-truth-dir data/cold_start/ground_truth \
    --out-dir data/cold_start/trajectories_accepted
```

新采集的告警如果 `data/cold_start/ground_truth/` 下还没有对应标注，需要你自己补一份人工标注 ground truth（`remediation_type`/`suspect_service`/`route` 等字段，`kind` 字段也建议一起标——拒绝采样和后续验收都会用到），这是设计文档里"拒绝采样需要人工标注"这句话背后真实需要你投入的工作量，不是脚本能自动生成的；已有的 63 条不需要重复标注。

## 6. 真实 GRPO 训练

### 6.0 先把告警 + ground truth 转成 veRL 能读的数据集

`grpo/to_verl_dataset.py` 把 `data/clean/split/{train,held_out}` 的告警 JSON 跟
`data/cold_start/ground_truth` 的人工标注拼成 veRL `RLHFDataset` 能直接加载的
jsonl,`prompt` 字段复用 `AIops-agent/agent/agents/prompts.py` 的真实提示词函数,
跟 SFT 训练时喂的是同一套提示词。这一步的输出目录 `grpo/verl_data/` 不入库（体量大，
`.gitignore` 已排除），需要你自己在本地跑一遍：

```bash
python3 -m grpo.to_verl_dataset --alerts-dir data/clean/split/train --split train \
    --out grpo/verl_data/train.jsonl
python3 -m grpo.to_verl_dataset --alerts-dir data/clean/split/held_out --split held_out \
    --out grpo/verl_data/held_out.jsonl
```

`data/cold_start/ground_truth/` 下的标注把 `train`（74 条）/`held_out`（22 条）两个
切分**每条一份 GT 全部覆盖**，跑上面两条命令应该拿到 74 行 + 22 行，不会有告警因为
缺标注被跳过（脚本会把跳过的逐条打印出来，不是静默丢弃——如果你自己又扩了种子池，
新增的告警记得先按 `data/cold_start/ground_truth/_annotation_report.md` 里的方法论
补标注）。

### 6.1 veRL 接入现状

`grpo/verl_reward_adapter.py` 已经是可以直接用的适配层：veRL 真实的 `custom_reward_function` 是逐样本签名 `compute_score(data_source, solution_str, ground_truth, extra_info)`（已对照真实 veRL 源码 `verl/workers/reward_manager/naive.py` 核实调用惯例），这个模块从 `solution_str`/`ground_truth`/`extra_info` 还原出这条 rollout 的 `Trajectory`，调用 `grpo.reward_router.compute_trajectory_reward` 打分，组内方差挪到组内 rollout 收集完之后再算。`rollout.name` 用的是 `vllm`（不是 sglang），真实跑通过验证工具调用确实被正确解析（不是模型在空跑时自己编结果）。

**两个字段必须显式设置，复现时最容易漏掉**：`actor_rollout_ref.rollout.agent.default_agent_loop` 必须设成 `tool_agent`——veRL 默认是 `single_turn_agent`，不设的话多轮工具调用完全不会被触发（`ToolAgentLoop` 和工具解析器都不会被实例化，训练看起来在正常跑，实际上模型只生成一次就结束）；`actor_rollout_ref.rollout.multi_turn.format` 必须设成 `qwen3_coder`——veRL 默认是 `hermes`，解析不出 Qwen3.5 真实的工具调用输出语法。这两个字段 `grpo/train_grpo.sh` 里已经写好并加了详细注释，复现时直接用这个脚本启动，别自己从 YAML 另起命令，否则很容易漏设。

单卡场景下的显存拓扑（`GPU_MEMORY_UTILIZATION=0.3`、`MAX_MODEL_LEN=16384`、`train_batch_size=74`——对应真实数据集大小 74 条（=整个 train 切分），不是设计估算的 150/256 条——`rollout.n=6`（每条 prompt 采 6 条 rollout，全程共 74×6×15=6660 条 rollout），以及 `ppo_mini_batch_size=74`、三个 `*_micro_batch_size_per_gpu=1` 这几个 veRL 必填项，不设置直接拒绝启动）在 `grpo/train_grpo.sh` 每个变量旁边都写了原因，直接看脚本注释；这层适配是怎么调通的细节另见 [`训练踩坑记录.md`](训练踩坑记录.md)。这些参数是按单卡 A800/79GB 这一档实测调出来的——如果你的卡型号/显存不同，多半要重新过一遍同样的显存预算排查思路，不能直接照抄数值。

这套配置已经在单卡 A800 上真实跑完过一轮完整训练（`total_epochs=15`，`save_freq=5`/`test_freq=5`，第 5/10/15 步各存一份 checkpoint 并跑一次 held-out 打分，`max_actor_ckpt_to_keep=2` 只保留最近两份防止把数据盘写满；对应产出的 checkpoint 就叫 `aiops-qwen3.5-9b-grpo-step15`，已合并 + 起 vLLM + 接入 AIops-agent 做过真实评测，见第 7 节）。复现时直接：

```bash
bash grpo/train_grpo.sh
```

如果你换了机器型号/显存/数据规模，跑之前先看一遍训练日志确认没有 OOM/loss 异常，不要假设配置文件里的显存参数照抄就一定适配你的硬件。

`grpo/tests/test_verl_config.py` 有一个 shape test 专门防止"YAML 里的轮数上限"和"reward_router.py 里硬编的轮数上限"这两个数字漂移——如果你改了 YAML 里的 `max_assistant_turns`，记得同步检查 `grpo/reward_router.py` 里 `max_turns_truncation_penalty` 用的数字。

## 7. 真实评测

**这里有两套完全不同的评测系统，先分清楚，别混用**：

1. **AIops-agent 自己的 `eval/run.py`，跑在它 13 个真实 docker-compose 故障场景上**（`s1`/`s2`/`s3`/`s4`/`s_lowconf`/`s5_dup`/`s6_info`/`s7_hybrid`/`s8_fix_fail`/`s9_adv`/`s10_ranking`/`s11_dedupe`/`s12_race`）。真实的 zero-shot / Cold Start SFT / SFT+GRPO-step15 / Opus 四档完整对比,就是这套系统跑出来的（vLLM serving 各自的 checkpoint,Opus 档接的是真实 `AIops-agent/agent/agents/diagnose.py::diagnose()`），报告在 AIops-agent 独立 checkout 的 `reports/{aiops-qwen3.5-9b-base-zeroshot_20260910,opus_20260819,aiops-qwen3.5-9b-v9_20260908,aiops-qwen3.5-9b-grpo-step15_20260910}/`（本仓库同步镜像了一份在 [`artifacts/eval_reports/`](../artifacts/eval_reports/)，没有 AIops-agent 仓库权限也能直接打开）。
2. **本仓库自己的 `eval/run_eval.py`/`eval/run_baseline_comparison.py`，配套 `data/clean/split/held_out`（22 条合成种子）**。这套是给 GRPO 训练期间做 periodic held-out 验证用的（`grpo/to_verl_dataset.py` 那条链路），跟上面的四档对比是两件不同的事。`eval/run_baseline_comparison.py` 的模块 docstring 写得很明确：这个脚本目前只对 `eval/model_endpoints.py` 里的 `ScriptedMockEndpoint` 之类的 mock 端点跑通过加载/打分/对比/消融全流程，用来验证 harness 本身逻辑对不对。`aiops-agentic-rl/eval/reports/` 下现在放的就是这批 mock 结果。

`eval/model_endpoints.py` 的模块 docstring 里明确写了一条边界：真实端点的 `diagnose(alert, ground_truth=None)` 实现**必须忽略** `ground_truth` 参数——这个参数存在只是为了让 mock 端点能按脚本设定的准确率档位生成确定性结果,真实模型窥视这个参数就是评测泄漏。这条边界对将来谁要把 `run_baseline_comparison.py` 真正接上 checkpoint 依然适用。

**复现 AIops-agent 那套四档对比之前，先把评测口径统一好**：一是 `agent/config.py::MILVUS_COLLECTION` 是全局唯一、不按模型分区的集合名，`AIOPS_RAG_ENABLED` 默认开。依次评测多个 checkpoint 时，给每个 checkpoint 换一个独立的 `MILVUS_COLLECTION`，或者评测期间直接 `AIOPS_RAG_ENABLED=0`，拿到干净可比的数字。

二是纯统计口径上的差异：`aiops-qwen3.5-9b-v9_20260908`（SFT 档）这份报告是 37 行/13 场景，GRPO/Opus 两档是 23~25 行——想要严格同口径对比，给 SFT 这一档也补跑到 25 行（排查思路见第 9 节）。

三是 `pr_submission_rate`/`fix_verified=True` 这类自述字段不能直接采信：模型在代码修复没通过验证（`fix_verified=False`）的情况下，仍有不小概率在结构化输出里编造 `pr_created=True`，光看 Agent 自己的输出完全看不出是编的。复现时对每一个声明创建了 PR 的 case，都要拿 `gh api search/issues -f q="repo:<repo> is:pr created:<日期>"` 去 GitHub 上核对当时那个时间窗口有没有对应的真实 PR，不能直接把 `metrics.json` 自动聚合出的 `pr_submission_rate` 当真（详见 `训练踩坑记录.md` 相应小节）。

如果你想让本仓库自己的 `eval/run_baseline_comparison.py` 真正接上真实 checkpoint（而不是继续跑 mock），需要自己写真实的 endpoint 适配层替换掉 `eval/model_endpoints.py` 里的 mock 类，再指向部署好的 vLLM 服务；v9 真实 held_out 就是 22 条，不够就照第 3 节的方法扩量。评测口径就是 held_out 22 条 + AIops-agent `eval/run.py` 的 13 个真实 docker 场景（`data/ood_fixtures/` 下的 4 条 alert stub：dns_poisoning / long_gc_pause / slow_query / tls_cert_expiry，只作为告警格式参考，不进评测集）。跑 mock harness 验证流程本身的命令：

```bash
python3 -m eval.run_baseline_comparison --endpoints sft sft_grpo opus \
    --cases data/clean/split/held_out --out eval/reports/
```

## 8. 服务化部署：合并 LoRA、起 vLLM、切换 `AIOPS_MODEL`

训练跑完之后（或者你想先拿一个未微调的底座练一遍部署流程也可以），先把 checkpoint 合并成 vLLM 能直接加载的单体目录，再起服务。**SFT 和 GRPO 产出的 checkpoint 格式不同，合并方式也不同，别用错工具**：

```bash
# 1a. 只部署 SFT checkpoint：把 LLaMA-Factory 产出的 LoRA adapter（PEFT 标准格式，
#     adapter_config.json + adapter_model.safetensors）合并回 text-only 底座
python3 deploy/merge_lora.py \
    --base-model-dir /data/models/qwen3.5-9b-text-only \
    --adapter-dir saves/aiops-diagnose-qwen3.5-9b/lora/sft \
    --output-dir /data/models/aiops-qwen3.5-9b-merged \
    --attn-implementation sdpa   # 训练时用的是 sdpa（见第 2 节），merge 时要保持一致，否则报 FlashAttention2 未安装

# 1b. 部署 GRPO checkpoint（`aiops-qwen3.5-9b-grpo-step15` 这种）：veRL 保存的是原始 FSDP
#     格式（global_step_N/actor/ 下一个 model_world_size_*_rank_*.pt），不是 PEFT adapter，
#     merge_lora.py 用不了，要用 veRL 自带的 model_merger：
python3 -m verl.model_merger merge \
    --backend fsdp \
    --local_dir checkpoints/aiops-diagnosis-grpo/<你的实验名>/global_step_15/actor \
    --target_dir /data/models/aiops-qwen3.5-9b-grpo-step15

# 2. 起 vLLM endpoint（已原生支持 Anthropic Messages API，不需要额外的协议转译层），
#    MODEL_DIR 换成 1a 或 1b 的输出目录
MODEL_DIR=/data/models/aiops-qwen3.5-9b-grpo-step15 \
SERVED_MODEL_NAME=aiops-qwen3.5-9b-grpo-step15 \
bash deploy/vllm_serve.sh
```

`merge_lora.py` 用的是 `peft.PeftModel.from_pretrained(...).merge_and_unload()`，`lora_target` 不需要手动指定——`PeftModel.from_pretrained` 会自己从 `adapter_dir` 的 `adapter_config.json` 里读出真实训练时的 target_modules。合并 GRPO checkpoint 前先确认磁盘空间：`global_step_15/actor` 本身、以及 `model_merger` 的输出目录都是完整 9B bf16 权重（各约 17GB），两者会同时占用磁盘，合并完验证服务能正常起来之后，原始 `global_step_N` checkpoint 可以按需保留或清理。

`deploy/vllm_serve.sh` 已经配好两处容易漏的关键参数：
- `--enable-auto-tool-choice --tool-call-parser qwen3_xml`：**必须加**。不加的话，AIops-agent 发一个带 `tools` 的请求会被 vLLM 直接拒绝；但如果调用链路没有严格处理这个报错，模型会在完全没执行任何工具的情况下自己"编"出一整套看起来很真实的工具调用结果（编造的 CPU 数值、容器重启时间等），光看输出内容完全看不出来是编的。
- `--max-model-len 131072`：AIops-agent 真实的系统提示词 + Skill + RAG 检索结果 + 多轮工具调用历史，单轮 prompt 实测能到 10 万+字符，远超训练时单条样本的长度（`cutoff_len=8192`）；`claude` CLI 对不认识的模型名固定按 32000 output tokens 预留预算，`max-model-len` 太小会导致每一轮诊断在模型开始生成之前就被 400 拒绝。

服务起好后，直接把 `ANTHROPIC_BASE_URL` 指向这个 vLLM 服务（不需要 LiteLLM 或其它转译层），在启动 AIops-agent 进程**之前**设置：

```bash
export AIOPS_MODEL=aiops-qwen3.5-9b-grpo-step15   # 跟 vllm_serve.sh 的 SERVED_MODEL_NAME 一致
export ANTHROPIC_BASE_URL=http://localhost:8000   # 直接指向 vLLM，端口跟 vllm_serve.sh 的 PORT 一致
export ANTHROPIC_AUTH_TOKEN=any-non-empty-placeholder  # claude CLI 要求存在凭证变量才走这条路径，vLLM 默认不校验
```

**验证请求真的打到了本地模型，不要只看返回结果是否"合理"**：先记录 vLLM 服务日志里 `POST /v1/messages` 的当前行数（`grep -c "POST /v1/messages" vllm_serve.log`），跑一次诊断，再数一次行数看 delta——delta 为 0 就说明这次调用根本没走到本地模型（不管返回了什么）；delta 符合预期轮次数才说明确实是本地模型在处理。不要用响应里的 `cost_usd`/`usage` 字段判断路由对不对：本地 vLLM 不支持 Anthropic 风格的 prompt cache，每轮都要把不断增长的对话上下文原样重发，累积 token 数天然会比真实 Claude API 大得多，这两个字段本身就不可信。

回滚到 Claude Opus 很简单——把 `AIOPS_MODEL` 改回默认值 `opus`（或者 unset）、unset `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN` 即可，不需要停掉 vLLM。

## 9. 结果跟 v9 真实 headline 差很多时，先怀疑哪里

v9 真实 headline 就是 SFT service/kind/route = 0.5676/0.6757/0.4595 → GRPO step15 = 0.80/0.72/0.64、Opus 约 0.913 粗口径。**方向性验证的口径是 SFT → GRPO 的相对增量**（service +0.23、kind +0.05、route +0.18）。差得比较远时按下面顺序排查：

1. **先看 reward 方差日志，不是先看最终准确率**。`reward/anti_hacking.py::group_reward_variance` 和 `should_downsample` 是专门为这个场景设计的——如果某个场景类型的 GRPO 组内方差长期趋近于零，说明这批数据对当前策略"太容易"或"太难"，梯度贡献本来就有限,不是训练循环坏了。reward 权重是短跑+mock 迭代的定性选择，你的真实数据分布下如果观察到某一类场景方差长期为零，可以按 `should_downsample` 自行调整下采样阈值。
2. **重跑 `eval/ablations/` 下的两个 mechanism-level 消融脚本**（`no_prefix_split.py` 证明前缀拆分让终止样本占比上升、`no_credit_assignment.py` 证明细粒度信用分配让组内方差非零）。两个脚本都是直接调用 `data/cold_start/prefix_split.py`/`reward/` 的真实函数,把 `DEFAULT_TRAJ_DIR`/mock 轨迹路径换成仓库自带的 `data/cold_start/trajectories_v9_final`（63 条真实冷启轨迹）或者你自己扩量后的目录,重跑一遍确认两个机制性结论在你的真实数据上依然成立,再去怀疑更上层的训练超参。
3. **检查 `Diagnosis.evidence` 的引用合法性覆盖率**。如果你观察到 `reward/anti_hacking.py::is_evidence_traceable` 大量匹配不上，大概率是它的字符串匹配规则在你的真实工具输出格式下匹配不上——真实 `kubectl`/`curl` 输出的措辞可能跟 mock 轨迹里的合成文本不完全一致,这条规则的匹配逻辑需要根据真实观测格式微调。
4. **检查种子数据的分层是否名副其实**。v9 真实种子池就是 47 新采 + v8_base 28 保留 = 63 通过 → train 74 / held_out 22，如果你自己扩量后某一类根因（比如队列积压）质量过滤后剩得特别少，held-out 的分层比例会漂移，评测结果的可比性会受影响——回头看第 3 节产出的清洗/切分统计,确认每一档的量级。
5. **最后才怀疑训练超参和底座本身**。`sft/llamafactory_config/qwen3_5_9b_lora_sft.yaml`（LoRA r=16 α=32 bf16 lr=1e-4 cutoff_len=8192 epoch=3）/`grpo/verl_config/aiops_grpo.yaml`（batch=74 rollout.n=6 15 epoch=15 step gpu_memory_utilization=0.30 save_freq=5 ~12h）里标了 `[JUDGMENT]` 的数值（学习率、KL 系数、checkpoint 间隔等）都是沿用官方示例默认值或工程判断,不是针对这个任务专门调过的——如果前面 4 步排查完都没问题,再考虑做超参搜索。

复现验收标准：拿真实 v9 的四档报告作为"这一版训练闭环真的跑通了"的对齐参照——四组报告分别落在 `AIops-agent/reports/{aiops-qwen3.5-9b-base-zeroshot_20260910, opus_20260819, aiops-qwen3.5-9b-v9_20260908, aiops-qwen3.5-9b-grpo-step15_20260910}/`（镜像见 [`artifacts/eval_reports/`](../artifacts/eval_reports/)）。方向性验证只看 SFT → GRPO 的相对增量：service/kind/route 三维都应看到相对 SFT 的正向 delta（v9 记录的是 +0.23 / +0.05 / +0.18）；zero-shot 档（service/kind/route = 0.48/0.52/0.36）应该全面弱于 SFT 和 GRPO，如果你复现出来 zero-shot 反而不弱于 SFT/GRPO，大概率是评测顺序导致的 Milvus RAG 记忆污染（见 [`训练踩坑记录.md`](训练踩坑记录.md) §6.7），先按那一节的方法隔离记忆再重跑。Opus 是粗口径 0.913 参考。
