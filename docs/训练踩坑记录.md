# 训练 + 部署踩坑记录

> 这份文档记录的是**真实复现过程中**踩到的坑，不是设计文档里的理论风险提示。按"租卡 → 拉代码/数据 → 装依赖 → 训练 → 部署 → 接入Agent评测"的实际时间顺序整理，每个坑都写清楚：**报错长什么样、根因是什么、怎么解决的**。目的是让后面复现的同学少走这些弯路，不代表这是唯一解法——很多坑本质是"版本/环境撞车"，你遇到的具体报错文案可能不完全一样，但排查思路是通用的。

## 一、租卡与基础环境

### 1.1 A100 在国内是禁运的，只能选 A800

国内云 GPU 平台（AutoDL 等）的常规地区列表里根本看不到 A100，因为美国出口管制。别在"西北B区""北京B区"这类常规分区里翻，去找一个专门的**"A800专区"**分区 tab，里面才有 A800（性能跟 A100 几乎打平，够用）。

### 1.2 数据盘"可扩容 0GB"是硬限制，不是配置项

同一档 GPU（比如 A800-80GB）下，不同物理机挂载的数据盘规格不一样，有些显示"数据盘: 50GB，可扩容 0GB"——这是这台物理机本身没有余量了，不是能通过下单页面调出来的。多翻几台机器，找"可扩容"不是 0 的。90GB（50GB基础 + 40GB扩容）这个量级对"下载模型 + 装两套训练框架 + 训练中间产物"是够用的，但要养成"及时删除不再需要的大文件"的习惯（比如转完 text-only checkpoint 后立刻删掉原始多模态 checkpoint）。

### 1.3 租的 GPU"容器"套娃了一层，天然不支持嵌套 Docker

这台机器本身就是一个 Docker 容器（`cat /proc/1/cgroup` 能看到 `/docker/<id>` 路径），装 `docker.io` 后 `dockerd` 无法启动：

```
failed to create NAT chain DOCKER: iptables --wait -t nat -N DOCKER: ... Permission denied (you must be root)
...
Failed to create bridge docker0 via netlink: operation not permitted
```

哪怕加 `--iptables=false --bridge=none` 让 daemon 本身跑起来，`docker network create` 仍然会报 `operation not permitted`——**这是云平台不给这层容器 `CAP_NET_ADMIN` 权限，不是配置问题，没有绕过的办法**。`docker-compose` 起多服务栈必然要建自定义网络，所以在这种租赁的 GPU 容器里**跑不了 docker-compose 编排的真实环境**（AIops-agent 的 OTel Demo 全套服务、Milvus 等）。

**结论**：GPU 租赁机器只适合承载"纯计算"的部分（训练、推理服务），真实的 docker/k8s 业务环境（AIops-agent 的故障复现环境）要放到别的机器上跑，或者——像我们最后发现的——**如果本地开发机上已经有一套现成的真实环境，直接用本地的就行，不用额外折腾**。

## 二、代码与数据拉取（网络）

### 2.1 GitHub HTTPS 国内直连不通，且早就不是"抖动"级别的问题

`curl https://github.com`、`git clone https://github.com/...` 大概率直接 `Connection timed out`，反复重试没用。国内常见的第三方加速镜像（`ghproxy.com`、`mirror.ghproxy.com`、`hub.fastgit.xyz`）**已经大量失效**，找到还活着的镜像（比如 `gh-proxy.com`）速度也只有几 KB/s，克隆一个几十 MB 的仓库要跑十几分钟到半小时。

**真正的解法：SSH（22端口）到 github.com 通常是通的**（跟 443 端口分别走不同的封锁策略），远快于任何 HTTPS 镜像：

```bash
ssh-keygen -t ed25519 -C "your-key" -f ~/.ssh/id_ed25519 -N ""
# 把公钥加到 GitHub 账号级 SSH key（Settings → SSH and GPG keys），而不是仓库级 Deploy Key
git config --global url."git@github.com:".insteadOf "https://github.com/"
```

加完这条全局改写规则后，所有写 `https://github.com/...` 的地方（包括 pip 的 git 依赖）会自动改走 SSH，速度立刻恢复正常（几十 MB 仓库几分钟内搞定）。

### 2.2 GitHub Deploy Key 是仓库级的，一把 key 挂不了两个仓库

如果只需要访问私有仓库，用 Deploy Key（仓库自己 Settings → Deploy keys 里加）比账号级 key 更安全（权限更小）。但**同一把公钥不能同时挂在两个不同仓库的 Deploy Key 上**，报错是：

```
key is already in use
```

如果要访问多个私有仓库（比如主仓库 + submodule），要么生成多把 key 分别挂，并在 `~/.ssh/config` 里给每个仓库配一个 `Host` 别名分别指定 `IdentityFile`；要么干脆用账号级 key（能访问你账号下所有仓库，包括任意公开仓库，权限更大，但省心）。

### 2.3 HuggingFace 新的 Xet 存储后端会绕开你配的镜像站，直接连接海外服务器

即使配了 `HF_ENDPOINT=https://hf-mirror.com`，下载大模型时仍可能报错：

```
RuntimeError: Task error: File reconstruction error: CAS Client Error: Request error: HTTP status client error (401 Unauthorized), domain: https://cas-server.xethub.hf.co/...
```

这是 HuggingFace 新推的 Xet 分块存储协议，走的是独立于 `HF_ENDPOINT` 之外的 `cas-server.xethub.hf.co`，国内镜像站代理不到这一层。解法是直接禁用 Xet，退回传统 HTTP 下载（走得通 `HF_ENDPOINT` 镜像）：

```bash
export HF_HUB_DISABLE_XET=1
```

## 三、torch / CUDA / Triton 版本地狱

这是整个复现过程里**最花时间**的一段，本质是"pip 自动解析出来的最新 torch，跟这台机器实际能用的 CUDA 工具链，以及 Qwen3.5 用到的几个第三方加速库，三者互相不兼容"。按遇到的顺序记录：

### 3.1 系统 nvcc 版本跟 pip 装的 torch 内置 CUDA 版本不匹配，flash-attn 编译不了

`pip install torch`（不锁版本）默认装的是**最新版**（当时是 2.14.0，自带 cu13 系列依赖），但机器上系统级安装的 CUDA 工具链（`nvcc --version`）是 12.4（跟随基础镶像自带）。编译 flash-attn 时，`torch.utils.cpp_extension` 会做版本一致性检查：

```
RuntimeError: ('The detected CUDA version (%s) mismatches the version that was used to compilePyTorch (%s). Please make sure to use the same CUDA versions.', '12.4', '13.0')
```

**这条检查过不去就是过不去，编译直接被拒绝，不会去尝试"能不能兼容"。** 解法（选一条）：
- 把 torch 降级到匹配系统 nvcc 版本的版本（比如 `torch==2.5.1+cu124`，用 `--find-links` 指向对应 CUDA 版本的 wheel 索引页，注意这种带 CUDA 标签的 wheel 不在常规 PyPI 索引里，要用 `--find-links` 而不是 `--index-url`）
- 或者装一个匹配 torch 的 nvcc（`nvidia-cuda-nvcc-cu13` 之类的 pip 包），配好 `CUDA_HOME`

我们选了第一条，把 torch 降到 2.5.1+cu124。

### 3.2 降级 torch 之后，Qwen3.5 用到的 fla（flash-linear-attention）又跟 Triton 版本不兼容了

torch 2.5.1 锁定的配套 Triton 是 3.1.0（比较老）。而 transformers 库加载 Qwen3.5 时**无条件**要 `import fla`（这个库处理 Gated DeltaNet 线性注意力层，不是可选依赖，跟你用不用 flash-attn 无关）。试了 3 个 fla 版本，全部失败，报错形态还不一样：

- `flash-linear-attention==0.4.1`：能 import，但实际跑 Triton kernel 编译时崩：`RuntimeError: PassManager::run failed`
- `flash-linear-attention==0.4.2`：import 阶段就崩：`ValueError: 'STAGE' is not in list`
- `flash-linear-attention==0.5.2`（最新版）：`TypeError: Autotuner.__init__() got an unexpected keyword argument 'do_bench'`（用了比 Triton 3.1.0 新的 API）

**根因是 fla 这几个版本都是针对更新的 Triton 写的，跟 torch 2.5.1 锁定的 Triton 3.1.0 全系列不兼容**，不是换个 fla 版本能解决的。最终解法：**把 torch 换回最新版（2.14.0，配套 Triton 3.8.0），fla 用最新版（0.5.2）**——牺牲第 3.1 节的 nvcc 匹配（反正后面训练用 `sdpa` 而不是 `flash_attn: fa2`，就不需要编译 flash-attn 了，nvcc 版本对不对齐不再重要）。

### 3.3 deepspeed 跟新版 torch 的算子注册 API 不兼容

装了新 torch 之后，任何触发 `import deepspeed`（哪怕只是被间接 import，你的训练配置根本没启用它）都会崩：

```
TypeError: Autotuner.__init__() got an unexpected keyword argument 'do_bench'
# 或
ValueError: infer_schema(func): Parameter partition_sizes has unsupported type list[int]...
```

排查后发现：训练配置里 `deepspeed:` 那行本来就是注释掉的（单卡 80GB 显存够用，不需要 ZeRO），但 LLaMA-Factory 的某个 Qwen3.5 补丁代码路径会**无条件尝试 import deepspeed**（哪怕不用它），只要环境里装了这个包就会在导入阶段崩溃。既然确认训练配置根本不需要它——**直接 `pip uninstall deepspeed`**，问题消失，不用花时间去对齐 deepspeed 和 torch 的版本兼容表。

### 3.4 反复切换 torch 版本，会在环境里留下 cu12/cu13 两套残留 NVIDIA 库，互相打架

来回切了几次 torch 版本（2.14 → 2.5.1+cu124 → 2.14）之后，`pip list` 里同时存在 `nvidia-nccl-cu12` 和 `nvidia-nccl-cu13`（其他 `nvidia-*` 包也一样，cu12/cu13 两套并存）——pip 卸载旧 torch 时不会连带清理这些被其他包"顺带"装上的、名字不同但功能重复的包。表现是 import 阶段直接崩：

```
ImportError: .../torch/lib/libtorch_cuda.so: undefined symbol: ncclCommResume
```

**排查这类"undefined symbol"错误时，先怀�Kong是不是同一个库的多个版本混装了**，`pip list | grep -iE "nvidia|torch|triton"` 扫一遍，看有没有同名不同 cu 后缀的重复条目。解法很暴力但有效：把所有 `torch*`/`nvidia-*`/`triton`/`fla*`/`flash*` 相关包**一次性全部卸载干净**，再一次性重装，不要一个一个换。

### 3.5 最终跑通的稳定组合

`torch==2.14.0`(自带 cu130) + `triton==3.8.0` + `flash-linear-attention==0.5.2` + 训练配置里 `flash_attn: sdpa`（不装/不用 flash-attn 本体，标准注意力层走 PyTorch 自带的 SDPA，Gated DeltaNet 线性注意力层走 fla 的 Triton kernel）。**这套组合牺牲了 FlashAttention-2 带来的训练速度收益，但换来了整条链路的稳定**，对新手来说这个取舍是值得的——先跑通,再谈性能优化。

## 四、SFT 训练

### 4.1 text-only checkpoint 故意剥掉的 processor 文件，会导致 LLaMA-Factory 的多模态校验报错

`load_text_only.py` 按设计只保留纯文本权重，不保存 `preprocessor_config.json`（图像/视频预处理配置）。但启动训练时报错：

```
ValueError: Processor was not found, please check and update your model file.
```

**LLaMA-Factory 给 Qwen3.5 系列模板默认绑定了多模态校验逻辑，哪怕你的数据集里完全没有图片，它也会检查模型目录下有没有 processor 配置文件**——这个检查跟数据集内容无关，纯粹是"这个模型家族"级别的硬编码行为。解法：把原始多模态 checkpoint 里的 `preprocessor_config.json` 和 `video_preprocessor_config.json`（这两个文件很小，几百字节，不含任何视觉权重）复制回 text-only checkpoint 目录，不影响"剥离视觉塔省显存"这个目标，只是补一个满足校验用的空壳配置。

## 五、部署（merge LoRA + 起 vLLM 服务）

### 5.1 `merge_lora.py` 默认用 `flash_attention_2`，但环境里没装

跟训练时同样的坑，`--attn-implementation` 默认值是 `flash_attention_2`，训练时已经改用 `sdpa`，merge 脚本要记得同步加 `--attn-implementation sdpa` 参数，否则报 `ImportError: FlashAttention2 has been toggled on, but ... doesn't seem to be installed.`

### 5.2 vLLM 新版本已经原生支持 Anthropic Messages API，不需要 LiteLLM 转译层了

设计文档写的时候，vLLM 只支持 OpenAI Chat Completions 协议（`/v1/chat/completions`），而 AIops-agent 走的 Claude Agent SDK 只认 Anthropic Messages API（`/v1/messages`），两者协议不兼容，文档给的解法是加一层 LiteLLM Proxy 做翻译。**但我们装的 vLLM 0.28.0（写文档之后发布的新版本）已经原生实现了 `/v1/messages` 端点**，直接 `curl http://localhost:8000/v1/messages` 就能拿到标准的 Anthropic 风格响应（`type: "message"`、`content: [...]`、`stop_reason` 等字段齐全）。**这条坑的教训不是"怎么踩"，而是"任何写了具体版本号/协议细节的技术方案，实际操作前都要先验证当前版本是否还适用"**——不要机械地照抄文档里"需要 LiteLLM"这个结论。

### 5.3 vLLM 起服务不加工具调用参数，模型会"编造"工具执行结果，而不是报错

这是**最容易被忽略、也最容易误导人**的一个坑。如果 vLLM 起服务时没加 `--enable-auto-tool-choice --tool-call-parser <parser>`，直接给 `/v1/messages` 发一个带 `tools` 参数的请求会报错拒绝：

```
"auto" tool choice requires --enable-auto-tool-choice and --tool-call-parser to be set
```

**但如果调用方（比如 Claude Code CLI）压根没有严格处理这个报错、或者调用路径本身有 bug 导致这个报错被吞掉，模型会在没有任何工具执行的情况下，直接在一次生成里"编"出一整套看起来极其真实的工具调用轨迹**（包括具体的 CPU 使用率数字、容器重启时间戳等）。我们查 vLLM 服务端日志发现整个"诊断过程"只发生了 1 次 API 请求，才确认这是编的——**光看输出内容的"合理性"完全看不出来是不是真调用了工具**，必须用"记录调用前后请求计数的 delta"这种客观指标才能判断。

### 5.4 Qwen3.5 目前没有专门的 tool-call-parser，要用同系列的通用 parser

vLLM 内置的 tool parser 里没有 `qwen3_5` 专门的条目（毕竟是很新的模型），但 Qwen3 系列的工具调用文本格式是延续的，用 `qwen3_xml`（或 `qwen3_coder`，指向同一个底层解析类 `Qwen3EngineToolParser`）能正常工作。查 vLLM 支持哪些 parser，可以直接看包内 `vllm/tool_parsers/__init__.py` 里的注册表，或者 `ls vllm/tool_parsers/ | grep -i qwen`。

### 5.5 Claude Code CLI 对不认识的模型名会固定请求 `max_tokens=32000`，跟 vLLM 的上下文窗口打架

vLLM 服务起好、工具调用协议也配对了之后，实际跑 AIops-agent 还是全部失败，报错：

```
400 BadRequestError: This model's maximum context length is 32768 tokens.
However, you requested 32000 output tokens and your prompt contains at least 769 input tokens...
```

原因：Claude Code CLI 内部有一份"已知模型"的档案表（记录每个模型的 context window / 最大输出 token 数），查不到自定义的模型名（比如 `aiops-qwen3.5-9b`）时，会退回一个固定的默认值 `max_tokens=32000`。如果 vLLM 起服务时 `--max-model-len` 配得比较小（比如按训练时的 `cutoff_len: 8192` 的几倍配了 32768），输出预算 + 输入内容一相加就直接超限，**在模型还没开始生成之前就被拒绝**。解法：把 vLLM 的 `--max-model-len` 调大（比如 131072），给这个写死的 32000 留出足够余量。Qwen3.5-9B 原生支持到 262144，调大不会有兼容性问题，只是占用更多 KV cache 显存（80GB 显存完全够用）。

### 5.6 GRPO 训练实际用的这版 vLLM，对 Qwen3.5 纯文本架构的支持有两处遗漏

vLLM 给 Qwen3.5 的多模态孪生类 `Qwen3_5ForConditionalGeneration` 配好了 `IsHybrid`（mamba 缓存 block size 自动推导）和 `SupportsMRoPE`（多轮 rollout 用到的位置编码），但训练用的这版 vLLM 没把这两处补给纯文本类 `Qwen3_5ForCausalLM`（GRPO 实际加载的类）。报错分别是引擎启动阶段的 `AssertionError: mamba_block_size is not None`，和第一次真实 rollout 生成阶段 `_calc_mrope_positions` 里的 `AssertionError`（`req.mrope_positions is not None`）。这是这版 vLLM 对这个新架构真实存在的上游缺口，不是本项目训练配置的问题——修复只能在 vLLM 安装包本身打补丁：给 `vllm/model_executor/models/qwen3_5.py` 的 `Qwen3_5ForCausalLMBase` 补上 `IsHybrid`/`SupportsMRoPE` 两个 mixin 和对应缺失的几个方法（直接照抄同文件里 `Qwen3_5ForConditionalGeneration` 的实现；纯文本场景没有多模态输入，`get_mrope_input_positions` 可以简化成"三个 rope 维度都等于普通顺序位置"这一种退化情形）。这个补丁改的是 site-packages 里的第三方安装文件，没有随仓库提交，换新机器/重新 `pip install vllm` 大概率还会遇到同样两个 `AssertionError`，遇到时按上面思路直接改 vLLM 源码即可，先别怀疑是自己的训练配置错了。

### 5.7 veRL 默认是单轮 agent loop，不显式设置的话多轮工具调用完全不会发生

GRPO 训练跑起来后，日志里 `num_turns` 一直是 2.0（看起来像是"正常跑完一轮就结束"），但实际上工具调用从来没被解析、执行过。根因有两层，两层都要修：

一是 `actor_rollout_ref.rollout.agent.default_agent_loop` 的默认值是 `single_turn_agent`，只有数据的 `non_tensor_batch` 里显式带 `agent_name` 字段才会切换成别的 agent loop——`grpo/to_verl_dataset.py` 产出的数据没写这个字段，所以哪怕 `multi_turn.enable=True`、`tool_config_path` 也配好了，veRL 实际调的还是只生成一次就结束的 `SingleTurnAgentLoop`，真正的 `ToolAgentLoop` 和里面的 tool parser 从未被实例化过（用临时 debug patch 在 tool parser 的 `extract_tool_calls` 里加日志，实测跑两个 step 一行都没打印，证实了这一点）。修复：显式设置 `actor_rollout_ref.rollout.agent.default_agent_loop=tool_agent`。

二是即使切到 `tool_agent`，veRL 的 `multi_turn.format` 默认值是 `hermes`，它的解析器只认 `<tool_call>{json}</tool_call>` 这种语法；但 SFT 用的 `qwen3_5_nothink` 模板产出的是 Qwen 原生嵌套语法（`<tool_call>\n<function=NAME>\n<parameter=k>v</parameter>\n</function>\n</tool_call>`），两者不匹配导致解析器永远解析不出 tool_calls，每次 rollout 被误判为"未发起工具调用"直接终止。修复：切到 veRL 自带的 `qwen3_coder`（对应 `Qwen3XMLToolParser`，正则跟这套语法逐字节匹配，不用新写 parser）。

这两个字段 `grpo/train_grpo.sh` 里都已经显式设置好了，复现时直接用这个脚本启动就不会再踩；如果自己手写 veRL 启动命令，这是最容易漏掉、也最不容易发现（不报错、只是静默不生效）的两处。

## 六、接入 AIops-agent 项目 + 真实评测

### 6.1 API base / 模型路由的真实优先级，跟直觉不一样

想让 AIops-agent 调用本地部署的模型，第一反应是改 `.env` 或者 `export ANTHROPIC_BASE_URL=...`。但 Claude Code CLI/SDK 实际的配置来源不止这一处，且优先级顺序不直观：

- **最高优先级**：编程调用 `claude_agent_sdk.query()` 时，`ClaudeAgentOptions(env=...)` 传的字典，会在 SDK 内部**无条件合并进子进程环境变量**，覆盖掉其他任何来源。
- 项目级 `.claude/settings.json` 里的 `env` 块：**只有** `ClaudeAgentOptions` 构造时 `setting_sources` 参数包含 `"project"` 才会被读取（默认是全部加载，但如果代码里显式传了别的值，就不一定）。直接敲 `claude` 命令走的是默认全加载，所以会生效；通过 SDK 编程调用则看调用方代码怎么传这个参数。
- 用户本机 `~/.zshrc` 之类 shell 配置文件里 export 的环境变量：**优先级最低**，会被以上两者覆盖——但如果以上两者因为某种原因没生效（比如下一条踩的坑），就会退回到这里，而这里往往是"日常自己用的、连着真实付费 API"的配置。

**教训**：不要假设"改了 `.env` 或者 shell 里 export 一下"就一定生效，尤其是这个项目内部还封装了一层 SDK 调用（不是直接敲 `claude` 命令）。改完之后**必须验证**，不能靠"看起来跑通了"就认为配置生效了（下面 6.3 讲怎么验证）。

### 6.2 一行耦合的代码，导致同一个项目里"部分调用正确路由、部分调用悄悄漏到真实付费 API"

这是最隐蔽的一个坑，值得详细记录排查过程。表现：跑同一个诊断流程，有时候结果看起来完全正常（后来验证也确实是真实工具调用的结果），有时候却产生了几美元甚至十几美元的真实 API 费用（`cost_usd` 字段异常，`input_tokens` 高达几百万）。

排查发现根因是 `agent/core/sdk_runner.py` 里这一行：

```python
setting_sources = ["project"] if skills is not None else []
```

项目里两个 Agent 调用 `run_sdk()` 的方式不同：故障诊断 Agent 传了 `skills=` 参数（因为要用排查手册 Skill），代码修复 Agent 没传。**这行代码把"要不要加载项目级配置文件"跟一个跟配置完全无关的业务参数（是否使用 Skill）绑在了一起**——诊断 Agent 因为传了 `skills`，能正确加载 `.claude/settings.json` 里配的本地模型地址；代码修复 Agent 因为没传，`setting_sources=[]`（SDK 的"完全隔离"模式），完全不读项目配置，直接退回到本机 shell 环境里那份连着真实付费代理的配置——同一个项目、同一次运行，两个 Agent 走了两条不同的路由。

**教训**：这类"配置是否生效"跟某个**看起来毫不相关的业务参数**耦合在一起的 bug，非常容易被忽略，因为大部分时候(调用了传 skills 的那条路径时)一切正常，只有触发到另一条路径时才会暴露。排查这类"时好时坏"的问题，思路是**找出所有调用同一个底层函数的地方，逐一对比它们传的参数有什么不同**，而不是反复重跑同一个场景想靠运气撞出规律。

修复方式：不再依赖 `setting_sources` 这种"部分生效"的机制，改成在 `run_sdk()` 内部**无条件**构造一份 env 覆盖字典，通过 `ClaudeAgentOptions(env=...)` 强制注入——不管调用方传不传 `skills`，路由结果都一致。

### 6.3 怎么可靠验证"请求真的打到本地模型"——不能看 `cost_usd`，也不能看模型输出内容是否"合理"

踩了 6.2 的坑之后，我们总结出一套可靠的验证方法，比"看输出结果像不像"或者"看 `cost_usd` 字段"靠谱得多：

1. **先记录 vLLM 服务端日志里 `POST /v1/messages` 的当前行数**（`grep -c "POST /v1/messages" vllm_serve.log`）。
2. 跑一次要验证的调用。
3. **再数一次行数，看 delta**。如果 delta 是 0，说明这次调用根本没打到本地模型（不管它返回了什么结果，那个结果另有来源）；如果 delta 符合预期的轮次数，说明确实是本地模型在处理。
4. 如果怀疑请求漏到了某个真实的第三方代理，可以**故意拿一个明显无效的 token 直接 curl 那个真实代理的地址**，确认它会返回 `401`——如果你的正式运行全程没出现认证错误，就能反向证明没有走那条路径（如果真走了，因为 token 是假的，会立刻报认证错误，不会是现在这种"正常返回结果"的样子）。

**不要用 `cost_usd`/`usage` 这些字段判断有没有走对路由**：本地 vLLM 不支持 Anthropic 风格的 prompt cache，每一轮都要把不断增长的对话上下文原样重发，累积的 token 数字天然会比真实 Claude API（有 cache）大得多；CLI 对不认识的模型名做成本估算时，也可能拿错定价表——这两个字段的绝对数值本身就不可信，用来判断"有没有花真钱"或者"有没有走对模型"都会得出错误结论。

### 6.4 评测子指标的分母设计,会让"没做的事"从统计里消失,而不是被记为失败

看 `metrics.json` 里 `fix_success_rate`/`pr_submission_rate` 这类字段,分母（denominators）可能小到只有个位数,乍一看以为是"这批跑得少",但根因不是样本少——是这些指标的分母被定义成"实际触发了代码修复的次数",不是"应该触发代码修复的场景数"。

看 `eval/metrics.py` 的 `extract()` 函数就能看出来:

```python
triggered_code_fix = fix is not None
fix_verified: bool | None = None
if triggered_code_fix:
    fix_verified = bool(fix.get("verified"))
```

如果模型这一次决定不触发代码修复（比如走了低置信度兜底路由，或者只做了重启自愈），`fix_verified` 直接是 `None`——不进分子，也不进分母，等于这条数据"消失"了，不算失败，也不算成功。

这会导致一个反直觉的结果：哪怕某个场景本来就是设计成"必须触发代码修复才算合格"的，只要模型这次选择不触发，`fix_success_rate` 这一个数字完全看不出这次不合格——它只会让分母变小，不会让比率变差。想知道"该修复但没触发"到底发生了多少次，得自己去数「`triggered_code_fix=False` 但场景配置里写了 `expect_fix_verified: true`」的行数，不能只盯着聚合出来的那一个比率。

**教训**：看到一个"准确率/成功率"型指标分母很小，先确认清楚分母的口径到底是什么，别默认它等于"这批本来要测的全部样本数"。

### 6.5 场景的"期望路由"允许多选一,别拿你以为最难的那条当唯一及格线

同一个场景（比如某个"部署引发的服务退化，理论上要改代码才能根治"的场景），两次跑出来的 `route` 字段不一样——一次是 `code_fix_pr`（走完整代码修复流程），一次是 `auto_remediated`（只重启，没碰代码）——第一反应很容易判断成"这次退化了，模型偷懒了"。

但翻一下这个场景的期望配置（`eval/expected.json`）会发现：

```json
"expect_route_any_of": ["code_fix_pr", "online_op_and_code_fix_pr", "auto_remediated_and_code_fix_pr", "auto_remediated"]
```

`auto_remediated` 本来就在允许列表里——这个场景设计时就承认"重启也是一种可接受的止血手段"，两次跑出来 `route_ok` 都是 `True`，压根不算退化。

**教训**：判断"这次是不是没达到预期"之前，先去翻这个场景的期望配置写的是什么，别凭自己对"应该怎么处理"的直觉去判断对错——尤其是"多选一"式的期望配置，字符串不一样不代表结果不一样对。

### 6.6 判断"退化了"之前，先把同一批场景的原始数据摆出来逐场对比，不能只看单个场景

对比两个模型版本在同一批场景上的表现，发现某个场景从"完全通过"变成"没触发修复"，直觉上很容易直接写成"这个场景退化了，可能是大问题"。但只对比这一个场景，很容易漏看：同一批场景里，是不是也有别的场景反过来从"失败"变成了"通过"。

举一次真实复盘的例子，同一批 5 个"必须改代码才算通过"的场景，新旧两个版本各自的通过情况：

```
        场景A   场景B   场景C   场景D   场景E   合计
旧版本    通过    未触发  未触发  未验证  未触发   1/5
新版本    未触发  未触发  未触发  通过    通过     2/5
```

只盯着"场景A"看，会觉得"退化了，原来能过的现在不过了"——但把 5 个场景摆在一起看，合计其实是从 1/5 涨到 2/5，是净改善，只是换了一批能通过的场景。

**教训**：任何"这个场景退化了"的结论，一定要把同一批相关场景的原始数据（不只是这一个场景）全部摆出来逐场对比，再下"退化/改善"的判断——只看单个场景，永远得不出"整体是变好还是变坏"这个真正重要的结论。这种对比往往还涉及只跑了一次（n=1）的场景，单次结果本身就有随机性，更要放在整体里看，不能单独解读。

### 6.7 评测多个 checkpoint 之前，先检查它们是不是共享同一个 Milvus 记忆集合

`agent/config.py::MILVUS_COLLECTION` 是全局唯一、不按模型分区的集合名。如果你依次评测多个 checkpoint（比如先测完 SFT 再测 GRPO 再测 zero-shot），**每一轮评测产生的工单都会写进同一个集合**，后测的模型在诊断时能通过 Agentic RAG 检索到前面几轮评测里、由更强模型（甚至是 Opus 参照）写出的诊断和修复方案，测出来的分数不能代表模型真实的零样本能力，这个风险本身是真实存在的。

**真实 v9 四档对比的实际数字**（以 `AIops-agent/reports/aiops-qwen3.5-9b-base-zeroshot_20260910/metrics.json` 为准——这份文件是从当前磁盘上的原始 `multi_run_*.jsonl` 精确重算出来的，可复核）：zero-shot service/kind/route = 0.48/0.52/0.36，mttr_seconds_p50 = 403.58s，四档里全面垫底，明显弱于 GRPO 的 0.80/0.72/0.64（mttr 119.7s）——也就是说这一轮 zero-shot 评测**没有**观察到被 RAG 记忆污染抬分的情况，模型表现符合"零样本、没训练过"的预期。（早期版本的这一节曾经写过"zero-shot 反而不弱于 GRPO"，那个说法引用的是当时 `EVAL_LOG.md` 里的执行记录叙述，后来发现跟 `metrics.json` 的真实计算结果不一致，已经改成上面这段——以后碰到类似情况，永远以 `metrics.json` 为准，不要直接采信任何逐条执行记录里的叙述性汇总。）

**教训**：评测多档 checkpoint 之前，先确认清楚记忆存储是不是被复用了。给每个 checkpoint 换一个独立的 `MILVUS_COLLECTION`，或者评测期间直接 `AIOPS_RAG_ENABLED=0`，才能拿到互相隔离、可以公平对比的数字——这条坑本质上和 6.4/6.5 是一类问题：先搞清楚你测出来的这个数字，到底在测什么。

### 6.8 "模型自称已提 PR"不能直接信，一定要拿外部系统核对

真实评测中发现，模型在 `fix_verified=False`（代码修复没通过验证）的情况下，仍然在自述字段里写 `pr_created=True`。光看 Agent 自己输出的结构化结果完全看不出这是编的——只有拿 `gh api search/issues -f q="repo:<repo> is:pr created:<日期>"` 去真实 GitHub 上核对当时那个时间窗口有没有对应的新分支/新 PR，才能确认。核对下来的规律是：验证通过的修复，PR 声明基本是真的；验证失败的修复，模型有不小概率编造"已经提了 PR"来掩盖失败。

**教训**：任何"Agent 自称完成了某个外部动作（建分支/提 PR/发通知）"的字段，评测时都要找一个独立于 Agent 自身输出的外部信源去核对（`gh api`、`kubectl get`、`git log` 等），不能因为 JSON 格式正确、字段齐全就当真。这也是为什么 `reward/anti_hacking.py` 里"引用合法性"这类校验要做成规则匹配轨迹里的真实工具输出，而不是信任模型自己的结构化字段。

### 6.9 训练脚本里 `MODEL_PATH` 默认值决定了 GRPO 接的是哪个 SFT checkpoint

评测报告目录（`AIops-agent/reports/aiops-qwen3.5-9b-base-zeroshot_20260910/`, `aiops-qwen3.5-9b-v9_20260908/`, `aiops-qwen3.5-9b-grpo-step15_20260910/`, `opus_20260819/`）里的数字之所以能互相拼成一张对照表，是因为 GRPO 接着的正是 v9 的 SFT 合并模型：`grpo/train_grpo.sh` 里 `MODEL_PATH` 默认值指向 `aiops-qwen3.5-9b-v9-merged`。仓库里同时存在 `_v8`/`_v9`/无后缀这几份文件名相近的数据集与合并 checkpoint，肉眼看差不多，但训练链路真正走的是脚本默认参数指定的那一份。

**教训**：仓库里存在多份同类命名的数据集/配置文件时，先用 `git log --oneline --all`（不加 `-- <path>`）确认训练脚本里的默认参数（如 `MODEL_PATH`）实际指向哪一份，别假设文件名相近的几份都在用——训练脚本默认参数被改过的提交，往往比数据文件本身的提交更能说明"训练链路真正往哪个方向走了"。

## 结语

回看整条链路，真正"难"的不是任何单一个坑，而是**这些坑分布在完全不同的层次**（云平台权限限制、Python 包版本兼容、模型库的隐藏强制依赖、CLI 工具的内部配置优先级、协议兼容性），每一层出问题的报错信息往往跟真正的根因隔着好几层调用栈，很容易在错误的层次上反复打转。几条通用的排查心态，可能比记住某条具体的解法更有用：

- **遇到"看起来很像对但又有点奇怪"的结果，先怀疑是不是压根没跑到你以为的那条路径上**，而不是急着分析结果内容本身（6.2/6.3 这两条坑就是典型例子）。
- **版本报错不要死磕同一个方向反复试**——同一个包换 3 个版本都报不同类型的错，往往说明问题出在更上游（比如 3.2 节：不是 fla 版本不对，是 Triton 版本从根上就不匹配）。
- **一次性把环境里同类包全部卸载干净重装**，往往比一个一个排查残留冲突更省时间（3.4 节）。
- **写死具体版本号/协议细节的文档，实际操作前先验证当下版本是否还适用**（5.2 节），技术生态变化速度经常比文档更新速度快。
- **准确率类指标先看清楚分母的口径**，不要默认分母等于"这批应该测的全部样本数"（6.4 节）。
- **"退化了"这个判断，下结论前先把同一批场景的原始数据摆出来逐场对比**，单场景/单次的差异很容易只是"洗牌"而不是整体变差（6.6 节）。
