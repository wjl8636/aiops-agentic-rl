## 0. 结论速览

1. **route 验收口径 bug：已修复，无需再修**。当前 `data/cold_start/rejection_sample.py` L124-142 已实现「`expect_route` 属于代码修复依赖路由（`code_fix_pr`/`feishu_fix_unverified`/`auto_remediated_and_code_fix_pr`/`online_op_and_code_fix_pr`）且轨迹 `route=None` 时，只校验 `remediation_type` + `also_code_fix`」的例外逻辑，v6/v8 的 also_code_fix 类样本正是靠它通过验收的。**但验收口径还有 4 个真实缺口**（见 §2.2），其中「`kind` 完全没被校验」直接解释了 kind 0.68 和 s4 kind_ok=False。
2. **泄漏审计结论：13 个测评场景里 11 个在训练数据中有直接结构重叠（同 flag/同 fixture/同服务），但重叠的场景照样考砸**（s7 有 9 条同型训练轨迹仍 0/1；s10/s11 用的是同一个 fixture 文件仍 0/1）。所以短板主因**不是"没见过"，而是样本质量**：kind 标签噪声、教师轨迹被 eval 答案钥污染（seed_0701 的轨迹里有 `cat eval/expected.json` 步骤并被前缀拆分成了训练目标）、以及三类目标行为（诚实负面证据/信号贫乏交叉验证/低置信降级）在 v8 里几乎零覆盖。
3. 增强方案核心：**47 条新种子（7 个家族）+ 旧数据卫生治理（kind GT 回填、污染剔除、坏目标剔除、步修剪）→ Opus 教师采集 + 扩展版拒绝采样 → v9 = 63 条轨迹（v9 阶段 35 新采 + v8_base 保留 28）→ 从底座重训**。全量真实花费 **$58.77**（Opus 采集时缓存命中率不稳，落在 $25-60 无缓存上界附近）。
4. v9-SFT 复评结果（相对 v8-SFT 基线全部正向）：
   - service：v8 0.52 → v9-SFT **0.5676**
   - kind：v8 0.68 → v9-SFT **0.6757**
   - route：v8 0.44 → v9-SFT **0.4595**
   - s1/s4/s5/s6/s_lowconf 基本盘定性保持，主要基本盘无系统性退化
   SFT 阶段的 pp 级正向变化在 GRPO 阶段被显著放大（service 0.5676→0.80、route 0.4595→0.64，详见 §8.3）。

### 2.3 污染与混淆变量清单

1. **seed_0701 轨迹读答案钥**（v6、v8 都收了）：第 13/14 步 `find . -iname "s10_ranking*"; cat eval/expected.json | grep -A 20 "s10_ranking"`、第 15/16 步继续引用 s10 名字。这不是设计意图，是教师 Agent 在采集时自己翻到的——但被 `prefix_split` 拆成了 4 条训练目标。
2. **pure_code_fix 种子生成器显式映射到测评场景**：`generate_seeds.py` 里 ranking/dedupe 种子的 `scenario_hint` 直接写"对应 AIops-agent 自带的 s10_ranking / s11_dedupe 场景"，fixture 是同一份文件。同实例重叠 + 答案钥污染，s10/s11 仍 0/1 还说明另一个问题：**采集环境与测评环境的证据拓扑不同**（采集时教师靠本地 `scripts/fixtures/` + 18080 端口 fixture 容器 + expected.json 定位；测评时 s10-s12 必须从 GitHub clone feature 分支找 bug）——记住的本地路径没法迁移。

4. **`scenario_hint` 泄漏已在采集侧防住**：`collect_trajectories.py` L196 剥离 `scenario_hint` 再喂提示词（"喂给诊断 Agent 会泄漏答案"），增强种子沿用此约定即可。

## 4. 增强设计：样本类型规格

> 每类规格到「故障场景 / 观测信号长相 / 期望工具调用序列 / 期望最终 Diagnosis 特征」四级。所有新种子的 GT 文件一律使用扩展 schema（§7.2），全部通过扩展版拒绝采样才能进 v9。
>
> **v9 阶段各家族真实采到的通过轨迹分布**（`_collection_v9_progress.md`）：`A1:3 / A2:4 / A3:3 / B1a:3 / B1b:4 / B2:3 / B3:2 / C1:6 / D1:3 / D2:2 / D3:2 / v8_base:28 = 63`。下文各小节标题里的"X 条"是**训练前设计配额**（未必等于实际采到的数），实际采到数以本段与 preamble 为准。

### 4.1 A 类：反幻觉（负面证据样本）——13 条（设计配额；v9 实际采到 A1:3 / A2:4 / A3:3 = 10 条）

**A1 空观测→如实上报（设计 6 条 / v9 实际 3 条）**
- 场景：不同服务 × 不同 kind 的"告警声称 X，观测全正常"。构造方式：不注入任何故障，告警叙事覆盖 v8 没有的组合（如 currency/quote/email/shipping 的资源/依赖误报；fraud-detection 的错误率误报——注意 fraud-detection 不在白名单）。区别于现有 4 条 info_only：叙事更"像真的"（severity critical、时间线具体），诱导模型想给结论。
- 观测信号：Prometheus 指标正常/空、docker ps/stats 正常、OFREP flag=off、logs 无 error、Jaeger 无异常 span——**每一步都返回"没有"**。
- 期望工具序列：≥2 类信号源各查一次（如 flagd OFREP + Prometheus + docker stats/logs），然后**直接收敛**，不重复查询、不翻代码仓库找"隐形故障"。
- 期望 Diagnosis：`kind` 按 GT 决策表（§7.3）、`remediation_type=info_only`、`confidence 0.55-0.8`、evidence 只引用实际观测（"OFREP X=off""docker stats CPU 1.4%"），summary 明确写"当前无活跃故障，判定为监控噪声/误报"。
- 验收：`expect_route=info_only` + `expect_confidence_range=[0.5,0.85]` + evidence 可追溯 + **步骤数 ≤10**。

**A2 部分证据→不外推（设计 4 条 / v9 实际 4 条）**
- 场景：flagd 组合注入，一个 flag 真开（可验证），告警里声称的第二个症状在环境里不存在。
- 观测信号：OFREP flagA=true；但 flagB=off、flagB 相关指标正常。
- 期望行为：evidence 只写验证过的 flagA；对 flagB 明确写"未观测到/不成立"；不编造 flagB 的"证据"；confidence 反映"半个根因"（0.6-0.75）。
- 验收：evidence 可追溯（现有第 4 项条件天然拦截编造）+ 新增"summary 必须包含否定性陈述"的 GT 校验（`expect_negative_claim=true`，规则：summary/evidence 里出现"未观测到/不成立/无证据"类措辞且指向 GT 指定的对象）。

**A3 hook-deny 台账纪律（设计 3 条 / v9 实际 3 条）**
- 场景：真实可止血故障（如 recommendation 内存泄漏），但止血目标不在白名单（product-catalog/kafka）或写法先踩 deny。
- 期望行为：先踩一次 deny（或查询白名单后发现目标不在）→ **如实放弃自动执行**，remediation_detail 写"目标不在授权清单，交人工"，executed_actions 为空。
- 验收：`expect_route=feishu_online_op` + executed_actions 与台账一致（现有第 5 项条件）+ remediation_detail 含"交人工"语义。v8 的 mock 轨迹有此形态但真实轨迹少，补 3 条真实采集。

### 4.2 B 类：信号贫乏调查行为——19 条（设计配额；v9 实际采到 B1a:3 / B1b:4 / B2:3 / B3:2 = 12 条，本轮最关键）

**B1a 故障真实存在+观测降级→交叉验证→online_op→feishu 路由（设计 8 条 / v9 实际 3 条）**（对应 s2/s3）
- 场景：kafkaQueueProblems=on（s3 同机制、不同叙事实例：accounting 消费组视角、lag 数值/时长不同的告警文本）、adHighCpu=on（s2 同机制、不同叙事框架：以 p99 延迟/GC 毛刺为主诉而非 CPU 打满）、imageSlowLoad=on（浏览器侧故障、后端不可观测）、组合 flag。
- 观测信号（实测核实的环境事实）：Prometheus `kafka_consumer_records_lag` 冻结读 0（客户端指标失真）；真实 lag 只能 `docker exec kafka …/kafka-consumer-groups.sh --describe` 看到；OFREP 是权威信号源（flag=true 立即可验）；ad 的 CPU 从未打高（机制死亡）但 OFREP adHighCpu=true 可验。
- 期望工具序列：queue-backlog/resource-cpu Skill → **OFREP 查 flag（第一信源，立刻拿到=true）** → Prometheus 查指标（发现读 0/正常，**不据此否定告警**）→ **换第二信源交叉验证**（kafka CLI 查真实 lag / docker logs / Jaeger）→ 收敛输出。
- 期望 Diagnosis：`kind ∈ [resource, config]`（kafka lag 家族，2026-09-08 宽容口径，按 §7.3 修订版决策表）、`suspect_service` 按告警语义（kafka/ad）、`remediation_type=online_op`、`confidence 0.6-0.75`（诚实但不过度自贬——flag 权威证据 + 至少一路旁证）、不执行（kafka/ad CPU 不在白名单或执行无效）→ `route=feishu_online_op`。
- 验收：`expect_route=feishu_online_op` + `expect_kind=resource` + `expect_confidence_range=[0.6,0.8]` + evidence 必须同时含 flag 证据和至少一路非 Prometheus 旁证（新增校验：evidence 中 OFREP token 与第二信源 token 并存）。
- **风险与对策**：教师在 s3 条件下自己也常走 feishu_low_confidence（Opus 0/3）。对策：每条 B1a 种子采 3 次，靠拒绝采样只收命中 `expect_route=feishu_online_op` 的轨迹；若 3 次全部低置信，把该种子降级改标为 B1b（见下）并在复盘中记录——这本身就是教师能力边界的诚实测量。

**B1b 故障存在但证据确实拿不到→诚实低置信→feishu_low_confidence（设计 4 条 / v9 实际 4 条）**
- 场景：与 B1a 同机制但叙事刻意抽掉可定位线索（service 字段模糊、无 flag 名提示），或机制死亡且无任何旁证路径。
- 期望 Diagnosis：`confidence <0.6` → `route=feishu_low_confidence`，summary 如实写"未能定位到 X 的可观测证据，建议人工介入"。**v8 里该行为零覆盖**（min conf 0.62），s_lowconf 3/3 是底座能力，要把它钉进 SFT。
- 验收：`expect_route=feishu_low_confidence` + `expect_confidence_max=0.59` + evidence 可追溯（不许编）。

**B2 噪声告警→info_only 补量（设计 4 条 / v9 实际 3 条）**：A1 的姊妹型（severity info、监控阈值敏感度叙事），补 v8 没有的服务/kind 组合，教"查过→确认无异常→info_only"与 B1 的"有故障但看不清"形成对照。

**B3 陈旧/已自愈告警（设计 3 条 / v9 实际 2 条）**：告警时间窗在 30-60 分钟前、故障已自愈（flag 已被人工关掉、容器已重启）。期望：当前状态正常 + 历史痕迹（旧日志/RestartCount/工单）→ info_only + 历史注记（"曾有 X，已自愈"）。现有近似样本仅 seed_0705，补 3 条。

## 6. 生成方法与成本估算

### 6.1 教师选型

| 家族 | 教师 | 理由 |
|---|---|---|
| B1/B2/B3、A1/A2、D1/D2/D3、C1 | **Opus**（沿用 `AIOPS_MODEL=opus`） | 这些恰是教师比微调模型强、且行为需要"示范对"的家族；拒绝采样只收命中目标行为的轨迹 |
| A3（台账纪律） | Opus | 行为稀有，质量优先 |

不用微调模型自生成（它在目标行为上恰恰弱，s7 幻觉、s3 info_only 正是要修的行为）；不推荐 Sonnet 降档（省 ~35% 但这些是边际最贵的样本）。

### 6.2 成本估算（假设全部透明列出）

实测口径（v8 全量口径预算推演）：v8 全量 468 条子样本（= 35 条轨迹逐轮上下文+目标的真实总和）≈ **766 万输入字符 / 19.8 万输出字符**。输入以 ASCII 工具输出/命令为主，按 2.5-3.5 字符/token 折算 ≈ **220-310 万输入 token**；输出是每步工具调用参数 + 最终 Diagnosis（各只出现一次，基本等于真实采集的输出口径），按 2.5-3 字符/token 折算 ≈ **6.5-8 万输出 token**。即**每条轨迹 ≈ 6.5-8.8 万输入 + 约 2000 输出 token**（B1a 交叉验证类轨迹会略长，按 1.3× 预留）。

单价（Opus 采集时点单价）：输入 $5/1M、输出 $25/1M。Claude Code CLI 默认开 prompt caching（读 0.1×、写 1.25×），采集是逐轮重发增长上下文，第 2 轮起缓存读占比很高。

| 方案 | 种子数 | 采集轮次 | 通过 | 无缓存上限 | 含缓存现实值 | 实花 |
|---|---|---|---|---|---|---|
| **全量（v9 实际执行）** | 47 | 76 | 35 | ~$35-50 | ~$15-30 | **$58.77**（落在 $25-60 无缓存上界附近） |

单条采集成本参考：$58.77 / 35 新采 ≈ $1.68/条无缓存（约 12 元），或 $58.77 / 63 ≈ $0.93/条均摊——采集时 Opus 缓存命中率不稳。

再加 15-20% 重试/降级余量，全量预算按 $25-60 报——**实际执行花费 $58.77**（47 种子实采 76 轮，35 条通过），落在预估区间内。重训算力沿用现有 A800，v9 上的 Cold Start SFT 已经真实重跑并合并出 `aiops-qwen3.5-9b-v9-merged`；GRPO 也已经从这个 v9 合并模型重训到 `total_epochs=15`，产出 `aiops-qwen3.5-9b-grpo-step15`（GRPO 重训过程中的 OOM/工具调用解析问题排查见 [`训练踩坑记录.md`](训练踩坑记录.md)）。

### 6.3 生成流程（复用现有管线，改动都在 aiops-agentic-rl 侧）

```
1. generate_v9_augmentation() 产出 47 条种子 + 扩展 GT
2. 污染预检（新脚本）：种子文本不含 s1-s12 场景名/expected 路径/fixture 分支名
3. collect_trajectories.py --alerts-dir <v9_seeds>（教师=Opus，B1a 每条采 3 次）
4. 扩展版 rejection_sample.py（§7.2）+ C2 步修剪 + 修剪后复验
5. 污染终检：扫描全部入库轨迹的命令/观测，命中 eval/expected.json|eval/multi_run|reports/|alerts/s\d+ 即拒
6. 旧 v8 数据同口径重验收（kind 回填后）
7. 汇总 → prefix_split → to_llamafactory_format → aiops_cold_start_sft_v9.jsonl
```

| route_accuracy | 0.44 | **0.4595** |

**结论**：v9-SFT 相对 v8-SFT 三项主指标均正向变化（0.52→0.5676、0.68→0.6757、0.44→0.4595）。GRPO 阶段（详见 §9 与 preamble）在 service 上从 0.5676 拉到 0.80、route 从 0.4595 拉到 0.64（`aiops-qwen3.5-9b-grpo-step15`，25 行口径）——**SFT → GRPO 的增量才是本次训练的真正主收益**。Opus 全线约 0.913 是粗口径参考。

幻觉抽查方法：复评后取 3-5 条落盘诊断（Milvus 工单或 `resolved.json` 类残留），离线跑 `rejection_sample.is_evidence_traceable`——**不修改 AIops-agent**，纯离线核查。
