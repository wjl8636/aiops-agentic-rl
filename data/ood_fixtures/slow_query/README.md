# OOD: 慢查询

**故障是什么**：一次发版给某个查询新增了过滤条件但没配套建索引，该查询在数据量大的场景下退化为全表扫描，占满数据库连接池，连带拖慢同一连接池上的其它查询，表现为接口 p99 延迟飙升，但错误率、请求量、服务自身 CPU/内存均正常。

**诊断 Agent 该看什么信号**：数据库侧的慢查询日志（`pg_stat_statements`/慢查询日志里 `mean_exec_time`/`calls` 排序找到耗时最长的查询）；对可疑查询跑 `EXPLAIN (ANALYZE, BUFFERS)` 看是不是走了 `Seq Scan` 而不是 `Index Scan`；数据库连接池的活跃/等待连接数（如 `pg_stat_activity` 里 `state='active'` 且 `query_start` 很久之前的连接数）；对照最近一次发版的 diff 里是否新增了查询条件但没加索引迁移脚本。

**为什么是 OOD**：`resource-cpu` skill 的查询清单看的是容器 CPU 使用率和流量对比，`dependency-error` skill 看的是应用层 5xx 和 Jaeger trace——两者都不会去看数据库执行计划或慢查询日志。这类故障的特征是"应用层指标基本正常、瓶颈完全在数据库执行计划这一层"，需要一套全新的诊断动作（EXPLAIN、慢查询日志、连接池等待队列），现有 4 个 playbook 都没有覆盖。

**Kind 枚举张力**：这里把最接近的 `kind` 标成 `"resource"`（写在 `scenario_hint` 里，不塞进真实 alert JSON），因为表现上是连接池资源被占满；但它既不是常规的 CPU/内存资源瓶颈（`resource-cpu`/`memory-oom` 关注的是容器层资源曲线），也不是简单的代码回归（`deploy_regression` 关注的是内存泄漏/逻辑 bug 而非缺索引），真正的判定依据（执行计划里的 `Seq Scan`）不落在现有任何一类 playbook 的核对清单里，是需要单独一类"数据层性能回归"诊断路径的场景。

**如何注入复现（sketch，留给后续接真实环境时补全）**：
1. 在目标数据库里建一张有一定数据量（比如几十万行）的表，故意不给某个高频过滤字段建索引。
2. 让 product-catalog（或一个最小化的复现脚本）对该字段发起过滤查询，触发全表扫描；也可以更直接地在一个调试端点里执行 `SELECT pg_sleep(3)` 或人为构造一条耗时查询，模拟"某条查询长期占用连接"的效果。
3. 用少量并发（比如 10-20 个连接）反复触发该查询，观察连接池等待队列变长、其它查询的延迟被间接拖慢。
4. 验证信号：`EXPLAIN ANALYZE` 该查询应显示 `Seq Scan` + 高 `actual time`；给字段建上索引后重跑同一查询延迟应显著下降，作为"确认根因"的对照实验。
