# OOD: GC 长暂停

**故障是什么**：JVM 老年代占用增长过快（例如一次发版新增了大对象批量构造逻辑），触发更频繁、更长的 Full GC 停顿，表现为请求延迟呈周期性秒级毛刺，而不是持续型的高 CPU 打满或内存单调泄漏到 OOMKilled。

**诊断 Agent 该看什么信号**：JVM GC 日志（`-Xlog:gc` 或 GC 日志文件）里 Full GC 的频率和单次暂停时长；延迟曲线的形态——是否呈"周期性毛刺"而不是"持续打满"（区分于 `resource-cpu` 覆盖的持续高 CPU）；内存曲线是否呈"锯齿状"（GC 后回落，区分于 `memory-oom` 覆盖的单调上升不回落）；配合发版记录看是不是最近一次改动引入了更重的对象分配模式（比如批量构造大对象、缓存未加大小限制但还没到 OOM 的程度）。

**为什么是 OOD**：`resource-cpu` skill 假设"CPU 飙高、延迟随流量同步上升"，`memory-oom` skill 假设"内存单调上升直到 OOMKilled"——GC 长暂停两者都不完全符合：延迟毛刺是周期性的、不是持续的；内存是锯齿状增长（GC 有效果，只是频率/耗时变差）、不是单调爬到 OOM。现有 2 个最相关的 playbook 的判定规则（"持续高 CPU 走流量对比"、"内存单调上升走发版关联"）在这个场景下都会给出误判方向，需要新增"看 GC 日志暂停时长分布"这个诊断动作。

**Kind 枚举张力**：这里把最接近的 `kind` 标成 `"resource"`（写在 `scenario_hint` 里，不塞进真实 alert JSON），因为表现上仍是资源/延迟异常；但它和现有 `resource` 场景（ad 服务的 `adHighCpu` 持续高 CPU）形状完全不同（周期性毛刺 vs 持续打满），如果训练/评测时把两者用同一个 `kind` 标签、同一套"kubectl top 权重更高"的信用分配规则去要求诊断 Agent，会引导它去查错的信号源（持续 CPU 曲线而不是 GC 日志暂停分布）。这是 OOD 集合里第三条指向同一个结论的证据：4 值 `Kind` 枚举在覆盖真实故障多样性时明显不够用，值得在后续迭代里扩展。

**如何注入复现（sketch，留给后续接真实环境时补全）**：
1. 给目标 JVM 服务（ad 服务的一个变体镜像）加一小段"自驾"逻辑：周期性地批量构造一批生命周期较长、体积较大的对象（比如一个大 `List<byte[]>`），模拟老年代占用增长过快。
2. 启动时加上 `-Xlog:gc*:file=/tmp/gc.log:time,uptime,level,tags` 或旧版 `-XX:+PrintGCDetails -Xloggc:/tmp/gc.log`，把老年代/新生代堆大小调小一些（比如 `-Xmx256m`）让 Full GC 更容易被触发。
3. 用固定 QPS 的负载生成器打流量，观察延迟曲线出现周期性毛刺，同时 `docker stats`/`kubectl top` 看到的 CPU 是"平时正常、毛刺时短暂升高"而不是持续打满。
4. 验证信号：GC 日志里 Full GC 次数和平均暂停时长应显著高于基线；调大堆或降低对象分配速率后毛刺应消失，作为"确认根因"的对照实验。
